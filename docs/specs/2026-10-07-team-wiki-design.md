# 팀 소통 위키 설계

- 작성일: 2026-10-07
- 상태: 검토 대기
- 대상 저장소: `team-wiki-engine`(public, 이 저장소) · `team-wiki-data`(private)

> 이 문서는 public 저장소에 들어간다. 팀 비공개 정보(접속 주소, 실명, 회의 내용)는 적지 않는다.

---

## 1. 배경

2026 오픈소스 개발자 대회(티맥스티베로 기업 과제)에서 6명이 저장소 4개(server, relay, worker, web)로
"AI 문서 관리 시스템"을 만들고 있다. 진행하면서 소통 문제가 세 가지로 드러났다.

1. **정보 비대칭** — 다른 저장소 사정을 알려면 담당자에게 묻고 답을 기다려야 한다.
2. **변경이 퍼지지 않는다** — 누가 무엇을 바꿔도 다른 사람은 모른다. 실제 사례:
   - worker의 `IndexingEvent`는 `traceId`를 읽는데, relay의 `EnvelopeAssembler`는 `traceId`를 보내지
     않는다(2026-10-06 코드 대조). 의도인지는 확인되지 않았다.
   - 공유 DB 접속 주소가 팀 메모와 개인 설정 파일에 서로 다르게 남아 있다.
3. **답이 사라진다** — 메신저에서 묻고 답한 내용이 남지 않아 같은 질문이 반복된다.

## 2. 목표와 성공 기준

**목표**: 팀원이 디스코드에서 물으면 근거와 함께 답하는 위키를, 사람 대신 LLM이 최신으로 유지한다.

| # | 성공 기준 |
|---|---|
| G1 | 봇 답변에 근거(위키 페이지 또는 `저장소@커밋:경로`)와 위키 기준 시점이 붙는다 |
| G2 | 같은 종류의 열린 동기화 PR이 없을 때, 코드 저장소에 머지된 변경이 다음 동기화(최대 12시간) 안에 위키 변경으로 올라온다 |
| G3 | 같은 종류의 열린 동기화 PR이 없을 때, `raw/`에 넣은 문서가 다음 동기화 안에 시간 순서대로 반영되어 올라온다 |
| G4 | 서버는 오라클 Always Free 한도 안, Claude API는 월 지출 한도 안에서 운영된다 |
| G5 | §11의 측정 지표가 사람 손 없이 쌓인다 |
| G6 | §12.3 relay 제거 시나리오를 통과한다 |

## 3. 범위

**포함**: 코드 저장소 자동 반영, 사람이 넣는 문서 반영, 디스코드 질의응답, 오라클 배포, 측정.

**제외**

- **노션 자동 수집** — 게스트 권한으로는 노션 통합을 만들 수 없고, 공유 링크는 로그인 없이 열면 본문이
  비어 있다(2026-10-06 확인). 필요한 노션 문서는 사람이 `raw/`에 넣는다.
- **카카오톡** — 단톡방 메시지를 읽는 공식 API가 없다. "메신저에서 정한 것을 문서로 옮기는 팀 규칙"은 보류.
- **봇의 위키 수정** — 봇은 읽기 전용이다. 위키를 바꾸는 주체는 동기화 작업 하나다.
- **여러 팀 동시 지원** — 다른 팀은 설정 파일을 바꿔 자기 인스턴스를 띄운다. 한 인스턴스가 여러 팀을 받지 않는다.

## 4. 핵심 결정

각 항목은 `docs/adr/`에 ADR로 남긴다.

| # | 결정 | 고른 것 | 버린 대안 | 근거 |
|---|---|---|---|---|
| D1 | 지식 축적 방식 | LLM 위키(문서가 들어올 때 정리본을 고친다) | RAG, 파인튜닝 | 팀 결정은 자주 뒤집힌다. RAG는 옛 결정과 새 결정 조각을 함께 꺼내 혼동하고, 파인튜닝은 갱신마다 다시 학습해야 한다 |
| D2 | 문서 반영 순서 | 파일명 날짜 순 | 넣은 순서, 한꺼번에 | 무엇이 무엇을 대체했는지 추적하려면 시간 순서가 필요하다 |
| D3 | 질문 창구 | 디스코드 봇 | 카카오톡 채널 챗봇 | 단톡방 API 없음. 채널 챗봇은 응답 5초 제한이라 콜백 구현이 추가로 필요하다 |
| D4 | 실행 위치 | 오라클 Always Free A1 + Claude API 키 | 개인 맥 + 개인 구독 | 상시 실행이 필요하다. 개인 구독을 팀 봇에 쓰는 문제도 피한다 |
| D5 | 저장소 구성 | 엔진 public / 데이터 private 분리 | private 하나 | 엔진은 공개해 재사용·포트폴리오로 쓰고, 팀 정보는 보호한다 |
| D6 | 위키 변경 반영 | 첫 2주 PR 검토 → 바로 반영 | 처음부터 바로 반영, 계속 PR | 검토 기간에 정확도를 재고 그 숫자로 전환을 판단한다 |
| D7 | 문서 반영 방식 | `raw/`에 push하면 서버가 반영 후 PR | 사람이 대화하며 반영, 디스코드 첨부 | 코드 반영과 같은 PR 흐름. 판단이 필요한 부분은 PR 본문에 적는다 |
| D8 | 위키 분류 | 현황·약속·결정·원본 요약 | 개념·엔티티 | 기획서가 아니라 저장소와 팀 결정이 중심인 프로젝트다 |
| D9 | 약속 단위 | 경계(누가→누구에게→무엇으로) + 대체 표시 | 저장소 쌍 고정 4개 | 구조가 바뀌어도(relay 제거 가능성) 버티게 한다 |
| D10 | 권한 분리 | AI는 파일만 고치고 git·GitHub 작업은 스크립트가 한다 | AI에게 Bash 허용 | AI가 명령을 실행할 표면을 없앤다 |
| D11 | 모델 | Claude Sonnet 5.5(`claude-sonnet-5-5`), 봇 effort `low` · 동기화 `medium` | Opus 5.5 | 비용 절반. 첫 주 측정으로 effort를 조정한다 |
| D12 | 구현 언어 | TypeScript(Node 22) | Kotlin | discord.js와 Claude Agent SDK가 TypeScript를 1급으로 지원한다. Kotlin용 Agent SDK는 없다 |
| D13 | Claude 호출 방식 | Claude Agent SDK(TypeScript) | `claude` CLI 자식 프로세스 | 도구 허용을 권한 콜백으로 강제하고(허용 목록), 결과·비용을 타입으로 받는다. ARM 리눅스 동작을 P1에서 먼저 확인하고, 안 되면 CLI 방식으로 돌아간다 |

## 5. 전체 구조

```
 [사람] ── raw/에 문서 push ──▶ [team-wiki-data · private]
                                raw/  wiki/  metrics/  baseline.json
                                   ▲              │
                         PR(위키 변경)             │ pull
                                   │              ▼
 [코드 저장소 N개] ── fetch ──▶ [오라클 서버 · A1 2 OCPU / 12GB]
                                ├ 봇 (상시)
                                ├ 동기화 작업 (하루 2회)
                                └ team-wiki-engine (이 저장소)
                                   ▲
 [디스코드] ◀── 질문 / 답 ────────┘
```

| 구성요소 | 하는 일 | 쓰기 권한 |
|---|---|---|
| 봇 | 디스코드 질문을 받아 위키·코드를 읽고 답한다 | 없음(서버 로컬 기록만) |
| 동기화 작업 | 코드 변경·새 문서를 위키에 반영하고 PR을 만든다 | 데이터 저장소 브랜치, PR |
| 점검 | 위키 규칙 위반을 찾는다 | 없음 |
| 측정 | 사용량·정확도를 기록하고 주간 요약을 만든다 | 서버 로컬 기록, 동기화 PR에 포함 |

**흐름 세 가지**

1. **질문** — 봇이 데이터 저장소 main 사본에서 Claude를 읽기 전용으로 띄운다. 위키를 먼저 보고 부족하면
   코드 사본을 읽는다. 답에는 근거와 기준 시점이 붙는다.
2. **코드 반영** — 동기화 작업이 기준 커밋 이후 머지된 변경과 열린 PR 목록을 읽고 위키를 고쳐 PR을 올린다.
3. **문서 반영** — 동기화 작업이 `raw/`의 새 파일을 날짜 순으로 반영하고 별도 PR을 올린다.

## 6. 데이터 저장소 (`team-wiki-data`, private)

기본값은 관리자 개인 GitHub 계정의 private 저장소다. 팀원은 필요하면 읽기 권한으로 초대한다.

```
raw/                               사람이 넣는 원본. AI는 쓰지 않는다
  YYYY-MM-DD-<제목>.md               파일명 날짜가 반영 순서
  assets/                            이미지 등 첨부
wiki/
  index.md                         전체 페이지 목록 + 한 줄 요약. 봇이 가장 먼저 읽는다
  overview.md                      저장소 관계, 현재 단계
  status/<저장소>.md                되는 기능 · 진행 중 PR · 주 담당자 · 기준 커밋
  contracts/<보내는쪽>--<받는쪽>--<수단>.md    예: relay--worker--kafka.md
  decisions/YYYY-MM-DD-<제목>.md    결정 1건당 1파일
  sources/<raw 파일명>.md           원본 요약 + 영향을 준 페이지
  open-questions.md                아직 열린 것만
  log.md                           반영 이력. 덧붙이기만 한다
metrics/
  weekly/YYYY-Www.md               주간 측정 요약
baseline.json                      저장소별 기준 커밋, 처리한 원본 목록
```

### 6.1 페이지별 frontmatter

| 위치 | 필수 필드 |
|---|---|
| `status/` | `repo`, `baseline_commit`, `archived`(true/false), `owners`(최근 90일 커밋 수 상위 2명의 GitHub 아이디, 추정치), `updated` |
| `contracts/` | `producer`, `consumer`, `medium`(http / db / kafka / 기타), `status`(현행 / 대체됨), `superseded_by`(대체됨일 때), `evidence`(`저장소@커밋:경로` 목록), `updated` |
| `decisions/` | `status`(확정 / 대체됨 / 논의 중), `decided_at`, `superseded_by`(대체됨일 때), `sources`(raw 파일 목록), `updated` |
| `sources/` | `raw`, `date`, `affects`(영향을 준 페이지 목록), `updated` |

### 6.2 규칙

- **R1 원본 불변** — `raw/`는 사람만 쓴다. 서버의 Claude는 `raw/`를 읽기만 한다.
- **R2 근거 필수** — 위키의 사실 서술에는 `sources/` 링크나 `저장소@짧은커밋:경로`가 붙는다.
- **R3 지우지 않고 대체 표시** — 바뀐 결정·약속은 `status: 대체됨` + `superseded_by`로 남긴다.
- **R4 코드와 문서가 다를 때** — 현황·약속은 코드를 따른다. 결정 문서와 코드가 다르면 둘 다 적고 `open-questions.md`에 올린다.
- **R5 미결 한 곳** — 열린 항목만 `open-questions.md`에 둔다. 해소되면 관련 결정 페이지로 옮기고 지운다.
- **R6 비밀값 금지** — 비밀번호·키·토큰은 적지 않는다. 접속 절차는 적어도 된다.
- **R7 책임 승계** — 구성요소 제거 결정이 기록되면, 해당 저장소 코드에서 하던 책임을 표로 뽑아 결정 페이지에
  붙인다. 새 담당이 없는 책임은 `open-questions.md`에 올린다.
- 위키는 한국어로 쓴다.

### 6.3 `baseline.json`

```json
{
  "repos": {
    "server": { "commit": "<40자 SHA>", "archived": false },
    "relay": { "commit": "<40자 SHA>", "archived": false }
  },
  "raw_processed": ["2026-08-20-킥오프-회의록.md"],
  "updated_at": "2026-10-07T09:00:00+09:00"
}
```

기준은 동기화 PR 안에서만 바뀐다. PR이 머지되어야 기준이 앞으로 간다.

## 7. 엔진 저장소 (`team-wiki-engine`, public)

```
src/
  bot/        디스코드 연결, 질문 처리, 세션 저장, 사용량 제한, 메시지 분할
  sync/       저장소 fetch, 변경분 계산, Claude 호출, PR 생성
  claude/     Claude 호출 공통: 모델·effort·도구 권한·경로 제한·비용 기록
  lint/       위키 점검 4종
  metrics/    사용량·정확도 기록, 주간 요약
skills/
  wiki-schema/   위키 구조와 R1~R7. 다른 스킬이 참조한다
  ask/           질문 답변 규칙
  sync-code/     코드 반영 규칙
  ingest/        문서 반영 규칙
deploy/
  setup.sh  update.sh  systemd/  secrets.env.example
config/
  team.example.json
docs/
  specs/  plans/  adr/
```

**스킬은 시스템 프롬프트로 넣는다.** 엔진이 Claude를 부를 때 해당 스킬 파일 내용을 시스템 프롬프트에 붙인다
(봇: `wiki-schema` + `ask`, 코드 반영: `wiki-schema` + `sync-code`, 문서 반영: `wiki-schema` + `ingest`).
모델이 스킬을 찾아 로드하는지에 기대지 않으므로 규칙이 항상 적용되고, Skill 도구를 열어 줄 필요도 없다.
파일은 `SKILL.md` 형식을 유지해 사람이 로컬 Claude Code에서도 같은 규칙으로 쓸 수 있게 한다.
데이터 저장소에는 스킬 파일이 없다.

### 7.1 설정 (`config/team.example.json`)

```json
{
  "repos": [
    { "name": "server", "url": "https://github.com/<조직>/<저장소>.git", "branch": "main", "status": "active" }
  ],
  "dataRepo": { "url": "https://github.com/<계정>/team-wiki-data.git", "branch": "main" },
  "discord": { "guildId": "", "channelIds": [], "opsChannelId": "", "adminUserId": "" },
  "schedule": ["09:00", "21:00"],
  "timezone": "Asia/Seoul",
  "reviewMode": "pr",
  "model": "claude-sonnet-5-5",
  "effort": { "bot": "low", "sync": "medium" },
  "limits": { "perUserPerMinute": 2, "dailyTotal": 60, "concurrent": 2, "botTimeoutMs": 300000, "syncTimeoutMs": 1200000 }
}
```

`status`가 `archived`인 저장소는 fetch하지 않는다. 그 저장소의 현황 페이지는 `archived: true`로 남는다.

## 8. 동기화 작업

**실행**: systemd 타이머(설정의 `schedule`). 서버에서 수동 실행도 가능하다.
동시에 하나만 돈다(잠금 파일).

**작업 사본을 분리한다**: 봇은 `data`(항상 main) 사본을 읽고, 동기화는 `data-sync` 사본에서 브랜치를 만든다.
그래서 동기화 도중의 미완성 변경을 봇이 읽지 않는다. 머지된 PR을 빨리 반영하려고 `data` 사본은 10분마다 pull한다.

### 8.1 순서

1. `data-sync`를 `origin/main`으로 맞춘다. 서버 사본에는 사람이 고친 내용이 없으므로 강제로 맞춘다.
2. 지난 동기화 PR의 결과를 측정 기록에 남긴다(§11 M1).
3. **코드 반영**
   1. 라벨 `wiki-sync:code`가 붙은 열린 PR이 있으면 건너뛰고 운영 채널에 "검토 대기 중"을 남긴다.
   2. `active` 저장소마다 fetch한다. 변경분은 `git log --first-parent <기준>..origin/<브랜치>`로 구한다.
      squash 머지도 잡기 위해 first-parent를 쓴다. 커밋과 PR의 연결(제목, 본문, 작성자)은 GitHub API로 가져온다.
      열린 PR 목록도 함께 가져온다.
   3. 변경분이 없고 열린 PR 목록도 그대로면 끝낸다.
   4. 작업 브랜치 `sync/code-YYYYMMDD-HHMM`을 만든다.
   5. Claude를 호출한다.
      - 도구: Read, Grep, Glob, Edit, Write만(권한 콜백으로 강제)
      - 읽기 허용 경로: `data-sync` 사본, 코드 사본들
      - 쓰기 허용 경로: `data-sync`의 `wiki/`, `baseline.json`
      - 지시: `wiki-schema` + `sync-code` 스킬 내용
      - 입력: 변경분 요약, 봇 질문 기록의 "위키에 없던 답"(§9.2)
   6. 점검(§10)을 돌린다. 위반이 있으면 목록을 주고 Claude에게 한 번 고치게 한다. 그래도 남으면 PR에 `점검 실패` 라벨을 단다.
   7. 커밋, push, PR 생성. `reviewMode`가 `direct`면 PR 대신 main에 커밋 하나를 push한다.
4. **문서 반영**
   1. 라벨 `wiki-sync:ingest`가 붙은 열린 PR이 있으면 건너뛴다.
   2. 새 원본 = `raw/` 목록에서 `baseline.raw_processed`를 뺀 것. 파일명 순으로 정렬한다.
   3. 파일마다 차례로: 분석(무엇을 대체·충돌·해소하는지, 영향받는 페이지) → `sources/` 작성 →
      결정·약속·미결 갱신 → `raw_processed`에 추가.
   4. 전부 끝난 뒤 한 번 더 확인한다. 이번에 바뀐 결정에 기대는 페이지를 다시 읽어, 앞 문서에서
      "현행"이라고 쓴 서술이 뒤 문서 때문에 낡지 않았는지 본다. 그다음 점검을 돌린다.
   5. 커밋, push, PR 생성.
5. 운영 채널에 결과를 한 줄 남긴다. 예: `코드 반영: PR 3건 → #12 생성 · 문서 반영: 없음 · 비용 $0.41`

### 8.2 PR 본문

- 반영한 코드 PR 또는 원본 문서 목록
- 바뀐 위키 페이지
- 새로 생긴 미결, 해소한 미결
- 문서 반영일 때: 문서별 분석(대체·충돌·해소)
- **AI가 확신이 낮은 부분**
- 이번 실행의 토큰·비용

### 8.3 실패 처리

| 상황 | 처리 |
|---|---|
| Claude 오류·시간 초과 | 작업 브랜치를 버리고 PR을 만들지 않는다. 운영 채널에 관리자를 멘션한다. 기준이 그대로라 다음 실행이 같은 범위를 다시 시도한다 |
| git·GitHub 오류 | 위와 같다 |
| 점검 실패가 남음 | 숨기지 않고 `점검 실패` 라벨을 단 PR로 올린다 |

## 9. 디스코드 봇

### 9.1 질문 처리

1. 허용된 서버·채널에서 봇 멘션을 받는다. 질문에서는 봇 자신의 멘션만 지운다.
2. 사용량 제한을 확인한다. 넘으면 이유를 답하고 끝낸다.
3. 스레드를 연다(이미 스레드 안이면 그 스레드). 스레드 ID로 세션을 찾는다. 세션은 7일 유지한다.
4. Claude를 호출한다.
   - 위치: `data` 사본
   - 추가 읽기: 코드 사본들
   - 도구: Read, Grep, Glob만
   - 지시: `wiki-schema` + `ask` 스킬 내용
   - effort: `low`
   - 제한 시간: 5분
5. 답을 2000자 단위로 나눠 올린다. 멘션 기능은 끈다(`@everyone`이 실제로 울리지 않게).
6. 기록한다: 시각, 응답 시간, 토큰, 비용, 답의 출처(위키만 / 코드까지), 위키에 없던 답 여부.
   **답의 출처는 모델의 자기 보고가 아니라 도구 호출 경로로 판정한다.** 코드 사본 경로를 읽었으면 "코드까지"다.

### 9.2 `ask` 스킬 규칙

1. `wiki/index.md` → 관련 페이지 → `open-questions.md` 순서로 읽고, 부족할 때만 코드 사본을 읽는다.
2. 답 끝에 근거와 기준 시점을 붙인다.
   ```
   — 근거: wiki/contracts/relay--worker--kafka.md · worker@a1b2c3d:src/.../IndexingEvent.kt
   — 기준: 위키 2026-10-07 09:00 반영 (server 1a2b3c4 · worker 5d6e7f8 · …)
   ```
3. 코드를 뒤져서 찾은 답에는 "위키에 없던 내용"이라고 표시한다. 봇은 질문과 답의 요지를 서버 로컬
   기록에 남기고, 다음 코드 반영 때 동기화 작업이 이 기록으로 위키 보강을 제안한다.
4. 모르면 모른다고 답한다. 근거가 없는 추측을 쓰지 않는다. 대신 현황 페이지의 주 담당자를 보고
   누구에게 물으면 되는지 안내한다.
5. 결정의 근거 문서가 위키에 없으면 "넣어 준 문서에 없다"고 말한다. 메신저에서만 정한 결정은 위키가 모른다.
6. 존댓말로 답한다.

### 9.3 보안

| 위협 | 대응 |
|---|---|
| 도구 오남용 | 권한 콜백으로 Read/Grep/Glob만 허용한다. 차단 목록(Bash, 파일 쓰기, 웹, 하위 에이전트, MCP)도 함께 둔다 |
| 비밀 파일 읽기 | 읽기 경로를 `data` 사본과 코드 사본으로 제한한다(심볼릭 링크를 풀어 실제 경로로 검사). 엔진 폴더, `/etc/team-wiki`, `~/.ssh`, `~/.claude`는 거부된다 |
| 코드 저장소의 비밀 파일 | 코드 사본 안의 `.env*` 읽기를 거부한다(`.env.example` 등 예시 파일은 허용) |
| 환경변수 노출 | Claude 호출에 디스코드 토큰과 GitHub 토큰을 넘기지 않는다 |
| 원본·코드 속 지시문 | 도구가 읽기 전용이라 피해가 답변 내용에 머문다 |
| 무단 사용 | 허용된 서버·채널에서만 답한다. 사용자당 분당 2회, 하루 전체 60회(매일 00:00 KST 초기화), 동시 2개 |

### 12.3 실전 시나리오: relay 제거

relay 제거가 결정되면 다음을 확인한다.

1. 결정 문서를 `raw/`에 넣으면 `decisions/`에 "relay 제거"가 생기고(`논의 중` 또는 `확정`),
   책임 승계 표가 붙는다. 표에는 최소한 발행(`OutboxDrainer`), 실패 분류·재시도(`FailureClassifier`,
   `BackoffPolicy`), 회수(`ZombieRecoveryScheduler`), 재발행(`DeadRecoveryScheduler`, `OutboxEndpoint`),
   지표(`RelayMetrics`)가 들어간다.
2. 담당이 정해지지 않은 책임이 `open-questions.md`에 올라간다.
3. 제거 코드가 머지되면 `relay--worker--kafka` 약속이 `대체됨`이 되고 새 경계 페이지를 가리킨다.
4. 설정에서 relay를 `archived`로 바꾸면 `status/relay.md`가 `archived: true`가 된다.
5. `traceId` 미결이 "누가 넣는가"로 갱신된다.

- 7일 넘게 회수되지 않고 돈다(Pay As You Go 전환).
- 월 비용이 지출 한도 안에 있다.

## 15. 위험과 남은 문제

| 위험 | 대응 |
|---|---|
| 메신저에서만 정한 결정은 위키가 모른다 | 봇이 "넣어 준 문서에 없다"고 답한다(§9.2-5). 팀 규칙은 보류 상태로 남긴다 |
| 비용 추정이 불확실하다(질문당 약 5만 토큰 가정) | 첫 주에 실측하고, 하루 상한과 월 지출 한도로 막는다 |
| A1 인스턴스 생성 실패(용량 부족) | 시간을 두고 재시도하거나 다른 가용 도메인을 쓴다 |
| Agent SDK가 ARM 리눅스에서 안 돌 수 있다 | P1 첫 작업으로 확인하고, 안 되면 CLI 자식 프로세스 방식(D13 대안)으로 간다 |
| relay 제거 시점·방식이 정해지지 않았다 | §12.3을 실제 결정 때 수행한다 |
| 팀원이 디스코드에 들어와야 한다 | 도입 전에 팀에 공지한다 |
| 주 담당자를 커밋 기록으로 추정하면 실제와 다를 수 있다 | 현황 페이지에 추정이라고 표시하고, 결정 문서가 담당을 정하면 그쪽을 따른다 |
